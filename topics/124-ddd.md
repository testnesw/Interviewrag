# 124 · Domain-Driven Design (DDD)

> Domain: Architecture Patterns · Level: Principal Solution Architect

## 1. Beginner Explanation
Domain-Driven Design (DDD) is an approach to software design that **puts the business domain at the center**. You model the software closely around real business concepts and language, working with domain experts, so the code reflects how the business actually works.

## 2. Architect-Level Explanation
A software design philosophy (Eric Evans) for complex domains, split into strategic + tactical patterns:
- **Ubiquitous Language**: a shared, precise vocabulary between developers and domain experts, used consistently in conversation *and* code — reduces translation errors.
- **Strategic design**:
  - **Bounded Context**: an explicit boundary within which a model + language is consistent; the same term can mean different things in different contexts (e.g., "Customer" in Sales vs Support). **The primary tool for microservice boundaries.**
  - **Subdomains**: **Core** (competitive differentiator — invest here), **Supporting**, **Generic** (buy/outsource).
  - **Context Mapping**: relationships between contexts (Partnership, Customer-Supplier, Conformist, **Anti-Corruption Layer**, Shared Kernel, Open Host Service, Published Language).
- **Tactical design (building blocks within a context)**:
  - **Entity** (identity over time), **Value Object** (immutable, defined by attributes), **Aggregate** (consistency boundary + **Aggregate Root** — the only entry point, enforces invariants), **Domain Event**, **Repository** (persistence abstraction), **Domain Service**, **Factory**.
- **Model-driven**: the domain model drives design; isolate it from infrastructure (hexagonal/clean/onion architecture).
- **Fit**: pairs naturally with microservices, event-driven, CQRS, event sourcing; best for **complex domains** (overkill for simple CRUD).

## 3. Real Enterprise Use Case
An insurance platform uses DDD: workshops with underwriters/actuaries build a **ubiquitous language**; the domain splits into **bounded contexts** — Policy, Claims, Billing, Underwriting — each becoming a microservice with its own model (where "Policy" means subtly different things). **Aggregates** (e.g., Claim as aggregate root enforcing claim rules) protect invariants, **domain events** (`ClaimApproved`) drive cross-context reactions via messaging, and an **Anti-Corruption Layer** shields the new model from a legacy mainframe.


## 5. Interview Questions
1. What is DDD and when is it worth it?
2. What is a bounded context and ubiquitous language?
3. What is an aggregate and aggregate root?
4. Entity vs value object?
5. What is an Anti-Corruption Layer?

## 6. Strong Interview Answers
- **What/when**: "DDD centers design on the business domain, using strategic patterns (bounded contexts, subdomains) and tactical patterns (aggregates, entities, value objects) to tame complexity. It's worth it for **complex core domains** with rich business rules — for simple CRUD it's over-engineering. The biggest payoff is a shared model + clean service boundaries."
- **Bounded context/ubiquitous language**: "A **bounded context** is a boundary within which a model and its **ubiquitous language** (the shared, precise vocabulary between devs and domain experts, reflected in code) are consistent. The same word can mean different things in different contexts, so we make the boundary explicit. This is my primary tool for defining **microservice boundaries** — one bounded context per service."
- **Aggregate/root**: "An **aggregate** is a cluster of related objects treated as one unit for consistency; the **aggregate root** is the single entry point that enforces the aggregate's **invariants** — external code can only reference the root, not internals. It defines a transactional consistency boundary (one aggregate = one transaction), which is key for correctness and for sizing units of change in distributed systems."
- **Entity vs value object**: "An **entity** has a distinct identity that persists over time even as attributes change (e.g., a Customer with an ID). A **value object** is immutable and defined entirely by its attributes with no identity (e.g., Money, Address) — two value objects with the same values are equal and interchangeable. Value objects reduce bugs by being immutable."
- **ACL**: "An **Anti-Corruption Layer** is a translation boundary that isolates your clean model from an external/legacy system's model — converting between them so the foreign concepts don't leak in and corrupt your domain. Essential when integrating with legacy systems or third parties while keeping your model pure."

## 7. Common Mistakes
- Applying DDD to simple CRUD (over-engineering).
- Anemic domain model (logic in services, data-only entities) — misses the point.
- Wrong bounded contexts → coupled microservices (distributed monolith).
- No ubiquitous language → dev/business translation errors.
- Huge aggregates (poor consistency boundaries, contention).

## 8. Trade-offs
| Aspect | Pro | Con |
|--------|-----|-----|
| DDD (complex domain) | clarity, boundaries | learning curve, effort |
| Small aggregates | less contention | more cross-aggregate coordination |
| ACL | model purity | translation overhead |

## 9. Production Best Practices
- Use for complex core domains; keep simple parts simple.
- Build ubiquitous language with domain experts (event storming).
- Bounded contexts → microservice boundaries; context mapping.
- Rich domain model; small, invariant-focused aggregates (one per transaction).
- Domain events for cross-context integration; ACL for legacy; isolate domain from infra.

## 10. Security Considerations
- Enforce invariants/validation in aggregates (domain-level integrity).
- Bounded contexts limit blast radius; per-context least-privilege.
- ACL validates + sanitizes external data at the boundary.
- Domain events carry only necessary data (avoid leaking sensitive internals).

## 11. Cost Optimization
- Focus engineering effort on the **Core** subdomain (differentiator); **buy/outsource Generic** subdomains.
- Right boundaries reduce rework/coupling cost; avoid over-modeling simple areas.

## 12. Troubleshooting Scenarios
- **Coupled microservices** → wrong bounded contexts; re-model with event storming.
- **Business logic scattered/buggy** → anemic model; move rules into aggregates.
- **Transaction contention** → aggregates too large; split into smaller ones.
- **Legacy concepts leaking in** → missing ACL; introduce translation layer.
- **Dev/business miscommunication** → no ubiquitous language; align vocabulary.

## 13. Hands-on Example
```python
# Aggregate root enforces invariants; value object is immutable
from dataclasses import dataclass
@dataclass(frozen=True)                 # Value Object (immutable, no identity)
class Money: amount: int; currency: str

class Order:                            # Aggregate Root (identity + invariants)
    def __init__(self, id): self.id = id; self._items = []; self._submitted = False
    def add_item(self, item, price: Money):
        if self._submitted:            # invariant enforced by the root
            raise ValueError("cannot modify a submitted order")
        self._items.append((item, price))
```

## 15. Azure Example
DDD maps cleanly to Azure microservices: each **bounded context** = a service on **AKS/Container Apps** with its **own datastore**, **domain events** published to **Service Bus/Event Grid** for cross-context integration, and an **Anti-Corruption Layer** (e.g., an Azure Function/adapter) fronting a legacy system — keeping each context's model isolated.

## 16. FastAPI / Python Example
```python
# Domain event raised by an aggregate → published for other bounded contexts
@app.post("/claims/{id}/approve")
async def approve_claim(id: str):
    claim = await repo.get(id)          # Repository (persistence abstraction)
    claim.approve()                     # aggregate enforces rules, raises ClaimApproved
    await repo.save(claim)
    await publish("ClaimApproved", {"claim_id": id})   # domain event → Billing context reacts
    return {"status": "approved"}
```

## 17. AKS Example
On AKS, each **bounded context** is a separately deployed service (own namespace/DB), communicating via **domain events** over Service Bus/Kafka. Context maps guide integration (ACL adapters as sidecars/services); aggregates define transaction boundaries within each service — DDD provides the *why* behind the microservice topology running on the cluster.

## 18. How to Remember
**"Model the business: ubiquitous language + bounded contexts (= microservice boundaries) [strategic]; aggregates/entities/value objects/domain events [tactical]; ACL isolates legacy; for COMPLEX domains only."**

## 19. Real-World Analogy
Designing a hospital by departments: each department (bounded context) — Cardiology, Radiology, Billing — has its own specialized language, procedures, and records, where even "patient" means something slightly different (a case vs an account). Staff and doctors agree on precise shared terminology (ubiquitous language), a lead doctor signs off on treatment decisions ensuring rules are followed (aggregate root), and a translator handles communication with an old partner clinic's incompatible system (ACL).

## 20. One-Page Cheat Sheet
- **What**: design centered on the business domain; for **complex domains** (not simple CRUD).
- **Ubiquitous Language**: shared precise vocabulary in conversation *and* code.
- **Strategic**: **Bounded Context** (model boundary = **microservice boundary**), Subdomains (Core/Supporting/Generic), Context Mapping (incl. **Anti-Corruption Layer**).
- **Tactical**: **Aggregate** + **Root** (invariants, transaction boundary), Entity (identity) vs **Value Object** (immutable), Domain Event, Repository, Domain Service.
- **Fit**: pairs with microservices / event-driven / CQRS / event sourcing; isolate domain from infra.
- **Avoid**: anemic models, huge aggregates, DDD on trivial domains.
