# 110 · Privileged Identity Management (PIM)

> Domain: Security & Identity · Level: Principal Security / Identity Architect

## 1. Beginner Explanation
Privileged Identity Management (PIM) makes powerful admin roles **temporary and on-demand** instead of always-on. Admins are *eligible* for a role and must **activate** it (often with MFA and approval) only when needed — reducing the risk of standing privileged accounts being abused.

## 2. Architect-Level Explanation
Just-in-time (JIT) privileged access governance in Entra ID (P2 feature):
- **Eligible vs active**: assign roles as **eligible** (can activate when needed) vs **active** (standing). PIM converts standing admin into JIT.
- **Activation**: user activates for a **time-bound** window, with **MFA**, **justification**, optional **approval**, and ticket number — then role auto-expires.
- **Scope**: **Entra ID roles** (Global Admin, etc.) and **Azure resource roles** (Owner/Contributor at subscription/RG) and PIM for **Groups**.
- **Controls**: max activation duration, require approval/approvers, require MFA, conditional access on activation, notifications.
- **Access Reviews**: periodic recertification of eligible/active assignments — remove stale access.
- **Auditing/alerts**: full activation history + alerts (e.g., too many admins, roles activated outside normal patterns).
- **Principle**: enforces **least privilege over time** and **zero standing privilege** — reduces attack surface (a compromised account usually isn't active-admin).
- **Break-glass**: keep 2 emergency accounts excluded from PIM/CA for lockout recovery.
- **Part of Zero Trust**: verify explicitly + least privilege for admin access.

## 3. Real Enterprise Use Case
An enterprise removes all standing admin: engineers are **eligible** for Contributor on their landing-zone subscriptions and activate JIT (MFA + justification, max 8h); Global Admin requires **approval** by a security lead and is limited to a short window; **Access Reviews** quarterly recertify eligibility; activations alert the SOC and flow to Sentinel; two break-glass accounts remain for emergencies — near-zero standing privilege, fully audited.

## 4. Architecture Diagram (ASCII)
```
   Admin assigned as ELIGIBLE (not standing/active)
        │ needs privilege ─► ACTIVATE
        ▼
   PIM activation: MFA + justification + (approval) + ticket
        │ grants role for time-bound window (e.g., 4h)
        ▼  auto-expires ─► back to eligible (zero standing privilege)
   Scopes: Entra roles · Azure resource roles · PIM for Groups
   Governance: Access Reviews (recertify) · alerts/audit ─► Sentinel/SOC
   Break-glass accounts (excluded) for lockout recovery
```

## 5. Interview Questions
1. What problem does PIM solve?
2. Eligible vs active assignments?
3. What controls gate an activation?
4. What are Access Reviews and break-glass accounts?
5. How does PIM support Zero Trust / least privilege?

## 6. Strong Interview Answers
- **Problem**: "Standing privileged accounts are a huge attack surface — if compromised, the attacker has permanent admin. PIM converts that to **just-in-time**: admins are eligible but only hold the role briefly when actively needed, drastically shrinking the window of exposure."
- **Eligible vs active**: "**Active** is standing access (always granted). **Eligible** means the person *can* activate the role on demand but doesn't hold it until they do. Moving admins to eligible achieves **zero standing privilege** — the core PIM value."
- **Controls**: "Activation can require **MFA**, a **justification** and ticket, **approval** by designated approvers, be **time-bound** (auto-expire), and be gated by Conditional Access. High-risk roles get stricter controls (approval + short duration)."
- **Access Reviews/break-glass**: "**Access Reviews** periodically force recertification of who's eligible/active, removing stale access automatically. **Break-glass** (emergency) accounts are 2 highly protected accounts excluded from PIM/Conditional Access so you can recover if policies or PIM lock everyone out — monitored closely."
- **Zero Trust**: "PIM operationalizes 'least privilege' and 'verify explicitly' for admins — no permanent power, MFA + approval per activation, time limits, and full audit. It assumes breach: even a stolen admin credential is usually not in an active-privileged state."

## 7. Common Mistakes
- Standing (active) admin roles instead of eligible/JIT.
- No approval/MFA on high-privilege activations.
- No break-glass accounts (risk of total lockout).
- No Access Reviews → eligibility sprawl.
- Not monitoring activations (no SOC/Sentinel alerts).

## 8. Trade-offs
| Choice | Pro | Con |
|--------|-----|-----|
| JIT eligible | zero standing privilege | activation friction |
| Require approval | strong control | slower access |
| Short windows | less exposure | frequent re-activation |

## 9. Production Best Practices
- Make privileged roles **eligible**, not active; short activation windows.
- Require MFA + justification; approval for highest roles.
- Access Reviews for eligibility recertification.
- 2 break-glass accounts (excluded, alerting on use).
- Alerts + audit → Sentinel; IaC/Graph-managed PIM settings.

## 10. Security Considerations
- Zero standing privilege; MFA + approval + Conditional Access on activation.
- Protect + monitor break-glass; separate admin (PAW) workstations.
- Alert on anomalous activations / too many admins.
- Combine with Identity Protection risk + least-privilege RBAC.

## 11. Cost Optimization
- Requires Entra ID **P2** — license privileged users appropriately.
- Reduces breach cost (biggest ROI); avoids over-licensing by scoping to admins.

## 12. Troubleshooting Scenarios
- **Can't perform admin action** → role not activated (still eligible); activate via PIM.
- **Activation denied** → approval pending / MFA not satisfied / CA block.
- **Locked out after policy change** → use break-glass account.
- **Stale admins persist** → no Access Review; schedule one.
- **Activation not audited** → ensure logs flow to Sentinel.

## 14. Terraform Example
```hcl
# Eligible (JIT) Azure resource role assignment via PIM
resource "azurerm_pim_eligible_role_assignment" "contrib" {
  scope              = data.azurerm_subscription.s.id
  role_definition_id = "${data.azurerm_subscription.s.id}/providers/Microsoft.Authorization/roleDefinitions/${var.contributor_role_id}"
  principal_id       = azuread_group.engineers.object_id
  schedule { expiration { duration_days = 90 } }   # eligibility window, not standing access
}
```

## 16. FastAPI / Python Example
```python
# App enforces that a sensitive operation requires a freshly-activated (JIT) admin claim
from fastapi import Depends, HTTPException
def require_jit_admin(claims: dict = Depends(verify_token)):
    # 'wids'/role claim present only when PIM role is currently active
    if "Admin.JIT" not in claims.get("roles", []):
        raise HTTPException(403, "activate privileged role via PIM first")
    return claims

@app.post("/tenant/rotate-keys")
async def rotate(_=Depends(require_jit_admin)): ...
```

## 17. AKS Example
AKS **cluster admin** (Azure RBAC for Kubernetes) is granted as a PIM-**eligible** role: operators activate JIT with MFA + justification to run privileged `kubectl` operations, then it auto-expires. No engineer holds standing cluster-admin; activations are logged to Sentinel for the SOC.

## 18. How to Remember
**"Eligible not active = zero standing privilege; activate JIT with MFA + justification + approval, time-bound + auto-expire; Access Reviews recertify; keep break-glass."**

## 19. Real-World Analogy
A bank vault that no employee can open at will. Tellers are on an approved list (eligible), but to enter the vault they must sign in, show ID (MFA), state why (justification), and get a manager's nod (approval) — and the door auto-locks after a set time (expiry). Two sealed emergency keys exist for disasters (break-glass), and the access log is reviewed regularly (Access Reviews).

## 20. One-Page Cheat Sheet
- **What**: JIT privileged access governance (Entra ID **P2**) — zero standing privilege.
- **Model**: **eligible** (activate on demand) vs **active** (standing); convert admin to JIT.
- **Activation**: MFA + justification + (approval) + ticket, **time-bound** → auto-expires.
- **Scope**: Entra roles + Azure resource roles + PIM for Groups.
- **Govern**: Access Reviews (recertify), alerts + audit → Sentinel, **break-glass** accounts (excluded).
- **Why**: Zero Trust least privilege over time; shrinks admin attack surface.
